# @pgfsm/sync-worker

The `fsmlet` runtime: the out-of-band worker that drives FSM instances forward
by running your actions, guards and delays. The HTTP API never blocks on or owns
worker lifecycle. `fsmlet` (kubelet — long-running node agent) picks up dispatch
entries that the scheduler (the `pg_cron` job, SPEC-003) assigns to it.

This package is a library. It ships no CLI bins: a pgfsm project embeds the
worker in its own entry point (`sync-worker/typescript/run-sync-worker.ts`,
generated by [`@pgfsm/cli`](https://www.npmjs.com/package/@pgfsm/cli)), which
calls `runFsmlet` with the project's compiled sync-operation registry.

## Install

```bash
npm install @pgfsm/sync-worker
```

## Usage

```typescript
import { runFsmlet } from "@pgfsm/sync-worker";
import {
  FSM_DEFINITIONS,
  SYNC_OPERATION_REGISTRATIONS,
} from "./sync-operation-registry-aggregate.generated.ts";

await runFsmlet(
  { connectionString: Deno.env.get("DATABASE_URL") ?? "" },
  SYNC_OPERATION_REGISTRATIONS,
  FSM_DEFINITIONS, // required: see "Startup check" below
  // optional 4th argument: { signal, maxConcurrency, fsmletId,
  // syncOperationRetry, … }
);
```

### When a guard, action, delay or input mapper throws

The step is retried in place, with the same event and the instance as it was
before the step, waiting 1 s, then 2 s, doubling (at most 30 s). Nothing else is
taken for that instance meanwhile, so its events stay in order. After
`maxAttempts` failed attempts the instance is set to status `error`, with
`{ kind, name, message, attempts, eventType }` as its error; nothing from the
failed step is applied, its invokes and timers are stopped, and a parent FSM
gets `xstate.error.actor.<invoke id>`. `error` is final, as in XState.

```typescript
await runFsmlet(dbConfig, SYNC_OPERATION_REGISTRATIONS, FSM_DEFINITIONS, {
  syncOperationRetry: {
    maxAttempts: 3, // default; 1 is XState's behaviour
    fsms: { creditCheck: { maxAttempts: 5 } }, // per FSM, all its versions
  },
});
```

The whole step re-runs, so keep sync operations pure (I/O belongs in actors).
Database and pgmq failures aren't counted: they're retried until they succeed. A
missing guard, delay or input mapper stops the fsmlet from starting (see
"Startup check"); a missing action is skipped, as in XState.

Upgrading from 0.5: an action or input mapper that throws used to be logged and
skipped; it now ends the instance in `error` after `maxAttempts`.

Upgrading from 0.6: the startup check also refuses a definition whose guard,
named delay or input mapper has no registration. At runtime these used to count
as false, send the event now, or give `null`.

### Startup check

Before it registers, the fsmlet reads `fsm_core.fsm_json` once and refuses to
start (throwing `FsmDefinitionCheckError`, which lists every problem) when an
FSM version it serves is:

- **missing**: not loaded; run `npx @pgfsm/ctl fsm load fsm` first;
- **ambiguous**: loaded more than once with different content;
- **drifted**: loaded with different content than the `fsm.json` this worker was
  generated from. A loaded version can't be changed: give the edited `fsm.json`
  a new version;
- **undigested**: missing from `fsmDefinitions`; regenerate the sync worker;
- **unimplemented**: its `fsm.json` calls a guard, a named delay or an input
  mapper with no entry in `SYNC_OPERATION_REGISTRATIONS` for that version;
  regenerate the sync worker (your stubs are kept). A missing action is still
  skipped at runtime, as in XState.

The check is mandatory; there's no option to turn it off.

Upgrading from 0.2: `runFsmlet`/`startFsmlet` take `fsmDefinitions` as a
required third argument, before `options`. Add `FSM_DEFINITIONS` to the import
from `sync-operation-registry-aggregate.generated.ts` and pass it as above.

Other exports:

```typescript
import {

} from "@pgfsm/sync-worker";

import type {
  FsmDefinitionDigest,
  FsmletHandle,
  FsmletOptions,

```

## Operating the database: `@pgfsm/ctl`

`@pgfsm/sync-worker` ≤ 0.2 also shipped the `fsmctl`, `pgcron` and
`fsmscheduler` bins. They moved to [`@pgfsm/ctl`](../fsm-ctl-ts/README.md) as
`pgfsmctl` subcommands (SPEC-005):

| Before (`npx -p @pgfsm/sync-worker -- …`) | Now (`npx @pgfsm/ctl …`)                |
| ----------------------------------------- | --------------------------------------- |
| `pgcron [-s <cron>]`                      | `db cron register [-s <cron>]`          |
| `fsmctl -c create -n <fsm> -V <v>`        | `instance create -n <fsm> -V <v>`       |
| `fsmctl -c resume\|send\|stop -q <id> …`  | `instance resume\|send\|stop -q <id> …` |
| `fsmscheduler [-p <ms>] [-s <secs>]`      | `scheduler run [-p <ms>] [-s <secs>]`   |

`runFsmScheduler`, `FsmSchedulerOptions`, `scheduleNextPending` and
`SCHEDULER_NOTIFY_CHANNEL` moved to `@pgfsm/ctl` too.

## Prerequisites

- **A Postgres database** with the pgfsm schema applied, the scheduler job
  registered once (`npx @pgfsm/ctl db cron register`), and the project's FSM
  definitions loaded (`npx @pgfsm/ctl fsm load fsm`, on every deploy)
