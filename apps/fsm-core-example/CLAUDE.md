# CLAUDE.md — FSM Examples (`apps/fsm-core-example/`)

Scoped guidance for example FSM definitions. Repo-wide conventions and session
protocol live in the root `CLAUDE.md` / `AGENTS.md`.

## FSM Definition Format

FSMs are versioned JSON files in `apps/fsm-core-example/fsm/` (e.g.
`creditCheck/`, `carVitals/`, `taskMachineConfig/`, `vitalsWorkflow/`). Each
version folder (`v01/`, `v02/`) contains:

- `fsm.json` — state machine definition
- `xstate-fsm.json` — XState 5-compatible format
- `machine.ts` / `machine-with-provider.ts` — XState machine definitions

`vitalsWorkflow/` is a reusable sub-workflow (asyncOperationType `fsm`) invoked
by other FSMs, rather than a standalone top-level FSM — otherwise it follows the
same layout. Definitions target **XState 5** semantics and are consumed by
`packages/fsm-compiler-ts/`.

Neither sync operation logic (actions/guards/delays) nor actor implementations
live here. They're in
[`test-apps/debug-only/`](../../test-apps/debug-only/README.md) (#405), a
project generated by `@pgfsm/cli` from this app's `fsm/`:

- `sync-worker/typescript/<fsmName>/<fsmVersion>/{actions,guards,delays}/`
- `async-worker/<lang>/<fsmName>/<fsmVersion>/actors/`, one subtree per language
  used by that version's `invoke` objects, plus each language's worker entry and
  manifest at `async-worker/<lang>/`

Its README shows how to point its workers at the SDK source in `packages/`
instead of the published packages, and how to regenerate an FSM after editing it
here. `machine-with-provider.ts` and the `*-test.ts` files import their stubs
from there by relative path. `create-async-logic`'s `sharedAsyncOperation/` pool
isn't part of that project (the CLI doesn't generate it).

The journey test imports `ActorWorker` from `@pgfsm/async-worker-sdk` by its
workspace name, so it always runs against local source.

## SPEC-011 end-to-end test (#536)

`spec011Parent/` and `spec011Child/` are test machines, not examples: one state
per SPEC-011 scenario (a child FSM stopped when its parent's state exits, a late
actor result, re-entry while an invoke is finishing). Their stubs are in
`test-apps/debug-only`, with sleeps the scenarios depend on.
`spec011Parent/v01/spec011-journey-test.ts` runs the whole stack from source in
one process (scheduler, fsmlet, gateway, TypeScript `ActorWorker`), loads both
definitions itself, and skips without `DATABASE_URL`. CI runs it in the
"SPEC-011 end-to-end" job; it takes about 30s, most of it waiting for late
results.

## SPEC-013 end-to-end test and creditCheck v03 (#587)

`spec013Input/` and `spec013Child/` are SPEC-013's test machines: an input
function over context and event (`mappedEcho`, built from the instance's `ssn`
and the START event's `eventPayload.requestId`), a static input, and an invoked
child FSM whose input is merged over its declared static context. The
`spec013Echo` actor returns its input, and `saveMapped`/`saveFixed` keep it in
context, so `spec013Input/v01/spec013-journey-test.ts` can check what each actor
received, for two instances with different contexts. CI runs it after SPEC-011's
journey test, in the same job.

`creditCheck/v03/` is `v01` recompiled with SPEC-013: its input functions become
`inputName`s with pre-filled input stubs in `test-apps/debug-only`. It's a new
version, not an edit of `v01`, because a loaded FSM version is immutable
(SPEC-006) and `v01`'s fsm.json would change.

In this runtime an input function's `event` is the processed message's
`eventData`, so an event's own fields are under `event.eventPayload`.
`input-mappers.json` next to a version's fsm.json is compile-time only (the
input functions' source, for pre-filling stubs).

## SPEC-012 end-to-end test (#545)

`spec012Cancel/` has one state per language, each invoking that language's
`spec012Work*` actor (5s of work) with a 1.5s `after` timer that exits it first.
Each actor waits on its cancellation signal and only writes a marker file (its
side effect, path passed through SPEC-013 input) if it wasn't cancelled.
`spec012Cancel/v01/spec012-journey-test.ts` runs the gateway with cancel
detection, the TypeScript worker in process and `test-apps/debug-only`'s Python
(`uv run`), Rust (`cargo build`, then the binary) and Go (`go run`) workers as
subprocesses, waits for each to log its registration, and checks per language:
one `cancel_acknowledged` row with reason `STATE_EXITED` and outcome `aborted`,
no marker file after the 5s, and the instance in `Abandoned` with no actor
event. `SPEC012_LANGUAGES` narrows the languages. CI runs it last in the
"SPEC-011 end-to-end" job, which installs uv, Go and Rust for it.

## SPEC-014 end-to-end test (#620)

`spec014Error/` and `spec014Child/` are SPEC-014's test machines. Each scenario
starts a new `spec014Error` instance in `Idle`:

- `FLAKY`, then `NEXT`: `spec014FlakyOnce` throws on its first attempt for each
  message (keyed on the worker's `{ queueName, msg }` argument), then passes.
  The worker retries `FLAKY` in place, so `NEXT` arrives in `AfterFlaky` and the
  instance ends in `Ordered`;
- `BROKEN`: `spec014AlwaysThrows` always throws, so after the default 3 attempts
  the instance is in status `error`, still in `Idle`, with
  `{ kind, name, message, attempts, eventType }` saved;
- `START_CHILD`: invokes `spec014Child`, whose entry action always throws. The
  test's fsmlet runs it with `syncOperationRetry.fsms.spec014Child.maxAttempts`
  1, so it errors on the first attempt and the parent's `onError` takes it to
  `ChildFailed`.

`spec014Error/v01/spec014-journey-test.ts` runs the scheduler and an fsmlet from
source (no gateway: neither machine invokes an actor). CI runs it after
SPEC-013's journey test, in the same job.
